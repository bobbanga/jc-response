# JC Response 使用说明

JC Response 用于在用户自己的 JC 账号下，按明确数量读取一批回盘，再查看、保存或导出同一批。用户自带 JC 账号。登录态、SQLite、raw JSONL 和 CSV 都只保存在当前 Windows 用户的产品目录。

契约是 `response_flow/1.1`。日常 AI 使用只走名为 `jc-response` 的 MCP，不回退命令行。数量必须由用户明确给出，单次 1–20 条、1 页。用户没说数量时先问，不默认 20。

首次开通前，程序给出范围说明。用户确认后，范围内的读取直接执行。滚动 24 小时预算是 10 次新读取、100 个记录额度和 400 次上游 HTTP 尝试，同时最多 1 个上游读取。退出登录即撤销开通，预算计数不会因此清零。预算用尽就停，不自动等待恢复后再读。

## 窗口

双击 JC Response 后可以查看连接状态、连接自己的 JC 账号、退出登录、接入 WorkBuddy，以及确认一次范围说明。

连接时会打开 JC 登录页。密码、验证码和二次验证由用户自己完成。只打开网页不算登录成功。退出登录只清除本产品保存在本机的登录态，已保存的回盘数据仍在。

## 读取一批

在对话中说：“使用 JC Response 读取一批 5 条回盘，不保存，不继续。”默认只读列表。要完整字段时，应在本次读取明确请求；已读取的 list_only 批次没有详情时，查看工具不会补抓。下一批由用户明确提出，数量仍须明确。

WorkBuddy 里对应的工具是 `jc_response_read_batch`。查看本批某一条用 `jc_response_batch_detail`，保存用 `jc_response_save_batch`，导出用 `jc_response_export_batch`。后三个工具只处理已经读到的同一批，不重新读取 JC。临时结果失效后不能自动重抓。

## 本地保存和 CSV

导出文件名默认是 `JC_response-<批次标识前 12 位>.csv`，契约名是 `JC_response.csv`。编码是 UTF-8，文件开头带 BOM。固定 30 列，顺序如下：

```text
response_id,freight_id,release_source,published_at,supplier_name,source_url,missing_fields,first_seen_at,last_seen_at,source_version,list_record_json,response_detail_json,freight_detail_json,negotiate_list_json,response_status,cargo_type,origin,destination,transport_type,container_type,quantity,weight,volume,quote_amount,quote_currency,quote_valid_until,contact_source,data_source,record_state,notes
```

字段没有可靠来源时保持为空。程序不根据业务常识猜测报价、联系人、港口或其他字段。`missing_fields=[]` 只表示当前检查的五个列表字段没有缺失。`contact_source` 写为 `JCTrans API only`，这是采集策略，不表示已经采到联系人。导出文件写在产品账号目录，不接受用户指定的任意绝对路径，也不覆盖已有文件。

当前版本不增加第 31 列，也不做旧表兼容。

## 当前版本不做的事

- 不采集 DOM 明文联系人。
- 不最终报价。
- 不自动提交报价。
- 不自动处理危险品。
- 不发送消息。
- 不做商业承诺。
- 不提供飞书写入、调度或推送。
- 不在 MCP 里开通权限、提高额度或清零预算。

## 升级后

先核对全部程序、说明及客户端实际加载的 Skill。安装验收只查 jctrans_status，不采集。已有登录态、已开通范围、本次服务端验证是不同状态。
